۷. ADR-0001: Kafka vs REST

فیلدمقدار
عنوانارتباط بین‌سرویسی با Kafka به‌جای REST
تاریخ۱۴۰۵/۰۸/۱۲
وضعیتAccepted
تصمیم‌گیرندگانتیم S3، با تأیید استاد درس دکتر ذاکری

زمینه (Context)

سرویس S3 (Payment Orchestration) با چهار سرویس دیگر ارتباط دارد و هر انتقال وجه ۵ تا ۷ گام دارد. در REST همگام، S3 باید در هر گام منتظر پاسخ بماند و اتصال HTTP باز نگه دارد. شکست یا کندی موقت یکی از سرویس‌ها مستقیماً کل انتقال را متوقف می‌کند. الگوی Saga که سند پروژه صریحاً اشاره می‌کند، با REST همگام به‌سختی پیاده می‌شود.

گزینه‌ها

گزینهمزایامعایب
۱. REST همگام ساده، ابزار تست فراوان، Swagger پخته Coupling زمانی، resilience ضعیف، Saga سخت، Idempotency فقط HTTP
۲. Kafka (AsyncAPI) Decoupling زمانی، resilience ذاتی، Saga بومی، Idempotency پیام زیرساخت اضافی، منحنی یادگیری، دیباگ سخت‌تر
۳. ترکیبی (REST + Kafka) خواندن ساده، نوشتن async دو مدل ذهنی، پیچیدگی قرارداد

تصمیم

گزینه ۲ (Apache Kafka با AsyncAPI) انتخاب شد. دلیل اصلی: ماهیت چندمرحله‌ای و غیرهمگام هماهنگ‌سازی پرداخت با الگوی Saga، REST همگام را نامناسب می‌سازد. این تصمیم با تأیید صریح استاد درس انجام شده است.

پیامدها

آسان‌تر می‌شود: پیاده‌سازی Saga و جبران، resilience، idempotency زنجیره‌ای، تطبیق پایان‌روز.

سخت‌تر می‌شود: زیرساخت اضافی (Kafka broker)، منحنی یادگیری، دیباگ با correlation_id، تست با testcontainers-kafka.

متن کامل ADR در فایل docs/adr/ADR-0001-kafka-vs-rest.md

۱۰.۲ بازنگری اسپرینت بعد (دو جمله)

در این اسپرینت، چالش اصلی هماهنگ‌کردن زیرساخت Kafka با Spring Boot 4.1.1 بود که با KRaft mode و تنظیمات JsonSerializer/Deserializer حل شد. برای اسپرینت بعد، اولویت با تکمیل orchestration کامل (S1 احراز + S2 بلوکه‌سازی) و افزودن تست‌های Integration با Testcontainers است.
